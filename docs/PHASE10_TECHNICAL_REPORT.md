# Swavlamban WAF ML: Challenge 3 Technical Report

## 1. Problem and approach

The project implements an ML-integrated open-source web application firewall. The edge combines deterministic rules and ML-derived risk signals, records structured decision evidence, enforces human-gated rule/model lifecycle controls, and exposes a secure operator API.

## 2. Architecture

**Request → EdgeWAF → decision/evidence → secure API → sanitized persistence → operator dashboard**

The runtime API is protected by signed bearer authentication and explicit roles. Runtime persistence uses a server-only Supabase REST adapter in production; raw body, raw headers, raw query material and source IP are excluded from persisted telemetry, with source identity represented by SHA-256 when present.

## 3. Phase 1–9 foundation

- deterministic rule pipeline and ML integration
- evidence-v1 decision explanations and detector contributions
- managed rule lifecycle with approval/deployment/rollback
- baseline, reviewed feedback, drift and champion/challenger controls
- authentication, RBAC, secret hygiene, fail-closed production settings
- Supabase RLS and privacy-hardening migrations
- local nginx HTTPS/TLS integration and deterministic Challenge 3 scenarios
- live Supabase schema/RLS/privilege verification

## 4. Phase 10 release candidate

Phase 10 adds an authenticated dashboard, a deterministic demo runner, a repeatable release-gate script, a presentation source, a technical report and a future-chat handoff package. The dashboard intentionally exposes only the safe operator surface and does not render raw request material.

## 5. Security evidence

The runtime accepts only validated signed bearer tokens, maps roles to explicit permissions, fails closed on invalid production configuration, applies standard browser security headers, and keeps service-role credentials server-side. Supabase runtime/control-plane tables use RLS, anonymous access is closed where required, and the Phase 9 migration scrubs legacy raw request fields.

## 6. Deterministic demo scenarios

The release candidate exercises benign allow traffic, known SQL/XSS patterns, a command-injection variant, repeated requests and API abuse/burst behaviour. The exact observed outputs are stored in the Phase 10 evidence JSON generated by `scripts/phase10_demo.py`.

## 7. Performance boundary

A 500-request in-process benchmark is retained from Phase 9. It excludes network/TLS/upstream time and therefore is not represented as Internet-scale performance.

## 8. Evidence boundary

Not claimed unless independently verified: public certificate issuance/rotation, public Internet HTTPS verification, ModSecurity/Coraza installation, and Internet-scale distributed failure/load testing.

## 9. Reproduction

```bash
python -m pytest -q
python -m compileall -q waf tests scripts
python scripts/phase10_demo.py
python scripts/phase10_master_exam.py
```

The release gate is hard-failed for critical verification defects and must not pass merely because documentation exists.
